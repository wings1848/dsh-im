# 重启后旧卡片的兜底体验

## 背景
卡片 nonce 只活在内存里（审计 P2-7 已知限制）。宿主重启后，屏幕上残留的键盘全部失效。
实测（模拟新进程拿旧 callback_data 点一下）用户看到的是：

```
这个菜单已失效或不存在。
```

**告知是对的，但断头了**：用户手里只剩一个死按钮，不知道该发什么命令才能继续。

## 改动
7 个命名空间的失效文案统一补上「怎么重新打开」：

| 卡片 | 新文案结尾 |
| --- | --- |
| `/menu` | 发送 /menu 可重新打开 |
| `/help` | 发送 /help 可重新打开 |
| `/status` | 发送 /status 可重新打开 |
| `/presetlist` | 发送 /presetlist 可重新打开 |
| `/conv` | 发送 /conv 可重新打开 |
| `/clear` | 发送 /clear 可重新发起 |
| 模型/推理 | 发送 /models 或 /reasoninglist 可重新打开 |

`/sessionlist` 已经带引导语（「请重新发送 /sessionlist 或 /session」），未改；
`approval-card` 的 UNKNOWN 文案是「该审批已处理或不存在，无需重复操作」——审批是一次性
决定，重复操作没有意义，保持原样更准确。

## 测试
新增 `test/channels/telegram/stale-card-notices.test.mjs`（9 例）：
- 7 个命名空间各点一次「未知 nonce」，断言提示里出现对应命令
- **外加一条覆盖检查**：扫描 src 下所有 `createCallbackNamespace('xx')`，
  断言每个前缀都有对应的旧卡用例。这条当场就抓到漏掉的 `r2`（推理卡与模型卡共用适配器
  但命名空间独立），已补。

红证：把 `/menu` 那条文案改回去，对应用例立即失败。

## 一个没做但值得知道的选项
更彻底的做法是**持久化卡片消息 id，启动时主动清掉旧键盘**。没做，因为要动状态存储结构 +
启动恢复流程 + 6 张卡，风险和收益不成比例：用户现在点旧卡会立刻被告知「发什么命令」，
已经能自愈。
